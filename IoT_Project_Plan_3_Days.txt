Detailed three day implementation plan for a two person team

Prepared 20 November 2026
Language: English
Resources: Windows laptop, 8 GB RAM, GPU with 2 GB memory
Status: Implementation plan. No data has been downloaded and no models have been trained.

1. THE PROJECT YOU WILL BUILD

Build an offline machine learning pipeline that reads published IoT network features, predicts normal traffic or an attack category, compares five models, and measures how expensive inference is on your laptop CPU. Package one selected model with its preprocessing and provide a command line demonstration.

Recommended dataset: the official Bot-IoT 5% subset. UNSW describes this as four files totaling approximately 1.07 GB and about three million records. It includes normal and botnet traffic, including DDoS, DoS, scanning, and theft activities. Obtain the actual files and descriptions from the official source, not an unidentified mirror. [S1]

Why this choice: a bounded official subset makes the acquisition step manageable within three days. Its class imbalance will still require careful treatment. The smaller training set proposed below is a project choice, not an official benchmark split.

Use one dataset, not all three. The assignment lists alternatives, and you have permission to choose. Compare Decision Tree, Random Forest, Logistic Regression, XGBoost, and a small dense neural network. XGBoost satisfies the XGBoost / LightGBM choice; implementing both is unnecessary for this deadline.

Main research question: which of these five models gives the best practical compromise between attack detection, false alarms, model size, memory consumption, and CPU inference latency on the selected Bot-IoT subset?

Important scope distinction: Bot-IoT is a botnet traffic dataset, but “botnet” is not automatically a separate mutually exclusive category alongside DDoS and reconnaissance. Use the dataset's actual labels. Do not invent a Mirai label or claim to identify every botnet family.

The result is an experimental intrusion detection prototype. It is not an antivirus, an automatic firewall, or a guarantee of security on a real IoT network.

3. HARDWARE AND COMPUTE BUDGET

Use CPU-only training. A GPU's 2 GB memory size does not establish its vendor, CUDA support, driver compatibility, or usefulness for this task. These small tabular models do not justify spending the deadline configuring it.

Resource rules
  - Close heavy applications while processing data or training.
  - Run only one training process at a time on an 8 GB machine.
  - Use two CPU threads for training initially; use one for the common inference benchmark.
  - Read CSV files in chunks of 50,000 rows. Reduce to 10,000 if needed.
  - Start with a 10,000-row smoke test, then approximately 100,000 training rows.
  - Increase training to at most 200,000 rows only if the first runs fit comfortably.
  - Preserve rare training classes when reducing the training set.
  - Aim to keep the Python process below roughly 3 GB RSS. This is a planning budget, not an enforced limit.
  - Reserve roughly 10 GB of free disk space for downloads, extracted files, temporary data, the environment, and outputs. Actual needs must be checked from the chosen files.

For large-file cleaning, use DuckDB on disk or chunked processing rather than loading every CSV into one pandas DataFrame. Configure DuckDB with memory_limit='1GB', threads=2, and a temporary directory inside data/interim. This memory setting is not a guarantee of the whole process's peak memory; monitor RSS. Never convert a full database query into pandas accidentally.

Fallback order if a run is slow or runs out of memory
  1. Reduce training rows and tree sizes.
  2. Reduce worker threads and CSV chunk size.
  3. Train models sequentially and release unused arrays.
  4. Remove optional experiments.
  5. Keep all five required model types with small configurations.

8. LABELS AND FEATURE CONTRACT

Primary target: attack category classification, using the actual release labels. The expected family structure is normal traffic, DDoS, DoS, reconnaissance, and theft; confirm the exact schema before writing a mapping. Keep an explicit label_map.json. Do not silently drop categories that appear in the files.

Secondary view: normal versus any attack. Derive this view from each multiclass prediction to avoid doubling the training workload. Preserve attack subcategories as analysis metadata so errors can be broken down further, where support is sufficient.

For normal rows, reconcile any category placeholders with the binary attack flag using the documentation. A category mapping should stop with an informative error when it sees an unknown label. Never guess that an unrecognized category means normal traffic.

Exclude from model inputs
  - Binary attack label, category, subcategory, and every target-derived field.
  - Row IDs, sequence numbers, CSV indices, and filenames.
  - Source/destination IP addresses in the baseline; they can encode the lab's attacker identity.
  - Absolute capture timestamps in the baseline; retain them as split metadata if useful.
  - Features whose construction uses future records, labels, or full-capture statistics unavailable at prediction time.

Keep plausible traffic features such as duration, byte counts, packet counts, rates, protocol, and connection state only after verifying their definitions. Ports can be legitimate features; retain or exclude them with an explicit reason rather than treating them as automatically safe or automatically forbidden.

Some derived dataset features may require global or time-window aggregation. Identify those dependencies. Either exclude them from the deployable candidate or explicitly describe the required extractor and its unmeasured cost.

Save feature_schema.json with ordered feature names, numeric/categorical types, missing-value policy, excluded-column reasons, label order, and schema version. The label order must be identical in model probabilities, tables, and plots.

9. CLEANING AND LEAKAGE RESISTANT SPLITTING

Implement the following order. Person B reviews the audit before training.

Step 1 — Normalize without learning from the data
  Strip accidental header whitespace, parse numeric fields consistently, normalize documented category spellings, and convert infinities to missing values. Count parsing failures. Do not replace all missing values with zero; zero can be a real measurement.

Step 2 — Identify duplicates and conflicting labels
  Create a canonical fingerprint from the actual input feature values, excluding labels and metadata. Use stable serialization with explicit missing-value handling. Calculate fingerprints after the chosen type conversions so identical model inputs are recognized. Do not include a unique row ID or timestamp merely to make every fingerprint different.
  Keep a deterministic representative for identical inputs with the same label. If identical inputs have contradictory labels, quarantine the group and report its size and class impact. This exclusion changes the evaluation population and must be disclosed.
  Perform this using disk-backed processing when necessary. Do not implement a separate deduplication pass inside each split; cross-split duplicates would survive.

Step 3 — Select the evaluation split policy before training
  If trustworthy session/capture/time grouping exists, prefer holding out independent groups or later captures. Do not equate “different CSV file” with “independent recording” without evidence. Check whether each class has enough independent groups to appear in train, validation, and test.
  If group separation destroys class coverage, do not move individual records across groups to conceal the issue. Document the tradeoff. For this three-day project, a stratified split of globally deduplicated records is an acceptable fallback, explicitly described as an easier within-dataset evaluation that may retain temporal correlation.
  If the release includes an official split, inspect its purpose and overlap first. Preserve it where appropriate, and obtain validation data only from its training portion; otherwise label your split as custom.

Step 4 — Make the splits
  Target 70% train, 15% validation, and 15% test with seed 42. For a simple stratified split, first hold out 30%, then divide that holdout in half. For group splitting, prioritize group separation; the ratios may be approximate. StratifiedGroupKFold can help when enough independent groups exist. [S10]
  Save immutable row IDs, source references, group IDs where available, and fingerprints in a split manifest. All five models use these same partitions.
  If any class has fewer than three independent examples/groups, a reliable three-way per-class evaluation is impossible. Report that constraint. Do not duplicate examples into multiple splits or silently remove the class. If this makes the main comparison infeasible, use the dataset fallback on Day 1.

Step 5 — Reduce compute without contaminating evaluation
  Downsample the training partition only. Start at approximately 100,000 total rows, retain all available rare training classes, and cap dominant classes to fit the budget. Save the exact selection and resulting class counts once, then reuse it for every model.
  Prefer keeping the full deduplicated validation and test partitions. Evaluate them in batches so they do not need to fit in RAM alongside training arrays. Their prevalence is that of the cleaned official subset, not real-world IoT traffic.
  If full holdout evaluation is too slow, use a fixed approximately proportional stratified sample chosen before training. Report its class supports and sampling fractions. Do not rebalance the headline test set. A separate deliberately enriched rare-class diagnostic sample is allowed only if clearly labeled and not mixed with the main metrics.

Step 6 — Fit preprocessing on training data only
  Numeric columns: median imputation. Remove wholly missing or constant features based on training data only.
  Categorical columns: an explicit missing token and OneHotEncoder(handle_unknown='ignore'). Keep categories low-dimensional; do not one-hot encode IP addresses.
  Logistic Regression and the dense network: StandardScaler on numeric inputs after imputation. Tree models: imputation and categorical encoding, without requiring scaling.
  Save the fitted transformers with the model. Validation, test, and inference use transform only. Pipelines reduce accidental leakage. [S3]

Step 7 — Stop on audit failure
  Assert zero overlap in row IDs and feature fingerprints across the final splits; also assert group disjointness when a group split is claimed. Check again after final feature selection or transformation if that creates identical inputs. Verify labels are absent from X, train supports cover required labels, and all post-transform numeric values are finite.
  For labels absent from an evaluation split, report support zero and unavailable class metrics. Do not silently omit them to inflate macro-F1.

Small dense neural network — Person B
  Input dimension: the fitted preprocessor's output width.
  Architecture: input -> Linear(64) -> ReLU -> Linear(32) -> ReLU -> Linear(K).
  K is the verified number of classes. The final layer outputs logits.
  Use CrossEntropyLoss on logits and integer labels; apply softmax only when probabilities are needed.
  Optimizer: Adam, learning rate 0.001, weight_decay=0.0001.
  Batch size: 256. Maximum 20 epochs. Stop after 3 epochs without validation macro-F1 improvement; restore the best checkpoint.
  torch.set_num_threads(2), DataLoader num_workers=0 on Windows, CPU tensors, float32 numeric inputs.
  Start with unweighted loss; try a bounded training-derived weighting scheme only if validation shows minority-class collapse. Log the exact weights. Avoid aggressive weighting plus aggressive oversampling without evidence.
  Record train loss and validation macro-F1 per epoch. Use model.eval() and torch.inference_mode() for inference.

11. HOW TO MEASURE QUALITY AND ANALYZE ERRORS

Report precision, recall, and F1 per class, with support. For the main aggregate comparison use macro-F1, because each class gets equal weight. Include weighted-F1 and accuracy as secondary summaries. Make absent-class handling explicit. [S11]

For binary normal-versus-attack reporting, attack is the positive class
  TP: attack predicted as attack.
  FN: attack predicted as normal.
  FP: normal predicted as attack.
  TN: normal predicted as normal.
  Precision = TP / (TP + FP).
  Recall = TP / (TP + FN).
  F1 = 2 * precision * recall / (precision + recall).
  False positive rate = FP / (FP + TN).

Report undefined denominators as unavailable and explain them. If there is little normal traffic, attach the normal support and avoid strong claims about false-alarm reliability.

Produce two confusion matrices for each model: raw counts and row-normalized percentages. Use true labels as rows and predicted labels as columns, with a consistent label order.

Error analysis procedure
  1. List the three largest off-diagonal confusion pairs by count.
  2. Also list large confusion rates so rare attacks are not hidden by DDoS volume.
  3. Separate attack-to-normal errors from attack-to-wrong-attack errors; their operational meanings differ.
  4. Inspect 10 to 20 representative error rows, including source/subcategory metadata.
  5. Compare distributions of a few plausible features for confused pairs.
  6. Offer explanations as hypotheses unless supported by actual observations.

Example of acceptable wording: “DoS and DDoS are frequently confused in our held-out subset; their rate and packet-count distributions overlap in these features.” Use this only if your results support it. Do not prewrite a finding as though it had already been measured.

Prepare these output tables rather than inventing results
  model_comparison.csv: model, seed, split_id, n_train, macro_precision, macro_recall, macro_f1, weighted_f1, accuracy, attack_recall, benign_fpr, fit_seconds.
  per_class.csv: model, class, support, precision, recall, f1.
  edge_benchmark.csv: model, device, threads, batch_size, p50_ms, p95_ms, rows_per_second, load_seconds, artifact_mib, idle_rss_mib, observed_peak_rss_mib.

12. WHAT EDGE PERFORMANCE MEANS HERE

Your Windows laptop measurements are a CPU feasibility study, not measurements on a Raspberry Pi, microcontroller, or production gateway. In the report use “laptop CPU proxy for edge feasibility.” If the teacher requires actual edge hardware, a physical-device run remains an unmet requirement until you obtain access to one.

A small artifact is not enough to prove deployability. Measure its runtime, memory, required feature availability, and software dependencies. A Python/PyTorch application may suit a gateway-class device but is not automatically suitable for a tiny MCU.

Benchmark protocol — implemented by Person B
  1. Record CPU model, physical/logical core counts, RAM, Windows version, power mode, library versions, and model hash. Run on AC power and close heavy applications.
  2. Use one CPU thread consistently: set OMP_NUM_THREADS, MKL_NUM_THREADS, OPENBLAS_NUM_THREADS and model-specific thread options before model libraries initialize. Record any runtime that does not honor the setting.
  3. Load one frozen model into a fresh process. Time loading separately.
  4. Use a fixed representative validation-derived benchmark input set, saved before final test evaluation. Avoid disk reads inside the inference timer.
  5. Warm up with 100 calls. Time at least 1,000 batch-size-one predictions using perf_counter_ns. Report median and p95 milliseconds per call; repeat the run three times.
  6. Separately measure batches of 256 rows and calculate throughput as rows divided by total measured seconds. Do not call batch throughput “single-flow latency”.
  7. Measure model-only inference on transformed inputs, and preprocessing-plus-prediction on raw feature rows. Report which boundary each number uses.
  8. Measure baseline process RSS after loading and sample RSS during processing. Report the observed peak and sampling interval; short peaks can be missed. Use a separate memory pass if sampling distorts latency.
  9. Sum the saved model, transformer, label-map, and schema file sizes. Report MiB consistently using 1,048,576 bytes per MiB. State that installed runtime/dependency disk space is excluded.
  10. Check prediction parity before and after saving/loading. If exporting or quantizing, check metrics again and label the exported variant separately.

This benchmark excludes packet capture, flow construction, aggregation windows, network transport, and alert handling. A model that uses completed-flow features cannot detect that flow before the required features become available. Avoid describing model inference time as end-to-end attack-detection delay.

Predeclare this selection rule on Day 1
  First identify the strongest validation macro-F1. Among models within 0.02 absolute macro-F1 of it, prefer lower preprocessing-plus-prediction p95 latency and smaller artifacts, while checking minority-class recall and benign false alarms.
  Provisional engineering targets: p95 below 10 ms per input row, bundle below 10 MiB, and observed inference RSS below 500 MiB on this laptop. These are project targets, not assignment requirements or measured achievements.
  If no model meets the targets, report the best tradeoff and missed targets. Do not change the targets after test evaluation to claim success.

Required limitations to discuss when applicable
  - Laboratory traffic and attack scenarios differ from real networks.
  - The official 5% subset and your training sample affect representativeness.
  - Deduplication/conflict removal changes the population being evaluated.
  - Row-based splits may retain correlated traffic even after exact duplicates are removed.
  - Rare normal/attack classes make some estimates unstable.

  - No evidence of generalization to new networks, new devices, or unseen attack families without a suitable held-out design.
  - Feature extraction and full detection delay are not included in the CPU inference numbers.
  - Laptop measurements do not prove Raspberry Pi or MCU performance.
